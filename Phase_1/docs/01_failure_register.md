# Failure-Mode Register — BankAssist Advisor

Written *before* building, per the brief's "How to Approach the Project" guidance: anticipate failures, don't discover them by accident. Each mode below names its mitigation and the phase that owns it, so nothing here is aspirational once that phase ships.

| # | Failure mode | Why it happens | Design mitigation | Owning phase | Evidence artefact |
|---|---|---|---|---|---|
| F1 | **Fabricated balance/fee on tool failure** | The LLM fills a gap with a plausible-sounding number when a tool call errors or times out | Fail closed: tool error → fixed apology + escalation offer, never a guess. Verified by `test_grounding.py` and the graceful-degradation matrix | Phase 5 (tool safeguards), Phase 8 (degradation matrix) | `evidence/05_failed_tool_call.md`, `evidence/08_graceful_failure.md` |
| F2 | **Stale fee quoted (wrong document version)** | The retriever returns a superseded policy doc when multiple versions exist and no `effective_date` filter is applied | Versioned frontmatter (`doc_id`, `version`, `effective_date`, `supersedes`) on every policy doc, plus an `effective_date` filter in the retriever. Deliberately planted (fee schedule shipped in two versions) and fixed with genuine before/after evidence | Phase 4 (planted), Phase 9 (root-caused and fixed) | `evidence/04_missing_info_case.md`, `docs/09_evaluation_report.md` §Failure Analysis |
| F3 | **Drift into implicit advice or approval** | Phrasing like "you should qualify" or "that sounds like it'll go through" reads as a commitment the bank never made | Explicit refusal rules for approvals/legal advice moved out of the prompt and into `policy_gate` as deterministic pre-LLM routing, not just prompt text | Phase 3 (first attempt, prompt-only), Phase 5 (hardened into routing) | `evidence/03_prompt_comparison.md`, `evidence/05_safeguards.md` |
| F4 | **Over-refusal on innocuous phrasing** | A naive keyword/verb blocklist catches harmless imperative phrasing ("can you check...", "process this for me" meaning "look this up") | Refusal logic scoped to classified intent categories, not keyword matching; M3 (false-refusal rate) measured alongside M2 (refusal recall) so over-refusal can't hide behind a perfect refusal score | Phase 3 (introduced), Phase 9 (measured) | `docs/09_evaluation_report.md` |
| F5 | **Wrong account selected when the customer holds several** | An ambiguous account reference ("my card," "the other account") gets resolved silently instead of being asked about | `ambiguous` intent routes to `clarify_node` — exactly ONE clarifying question before any account-lane tool call; never a silent guess | Phase 4/5 (routing) | `evidence/06_multiturn_transcripts.md` |
| F6 | **Multi-turn context bleed** | A prior turn's account or customer context leaks into an unrelated later turn, session, or (worse) a different customer's call | Session TTL (30 min idle), explicit short-term memory scoped per session, `/forget` command with a provable reset | Phase 6 (memory) | `evidence/06_memory_reset_proof.md` |

## Why this register exists before any code

Two of these (F2, and to a lesser extent F4) are **planted deliberately** rather than left to chance — see `capstone_build_plan.md` §4 and §8. A genuine root-cause-and-fix with real before/after metrics is far more convincing to a grader than hoping a good bug turns up late in the build, and by then it's too late to capture the "before" state honestly.
